# 判断記録（実装側）

設計キット v0.6 からの差分と、実装で決めたことを記録する。サイト固有の情報（ホスト名・実ACFのキー等）は書かない。

## D-001 CaseDocument に `relations` を追加 — 契約 v0.6.1 → v0.6.2（2026-11-18）
- 依頼者の指示：関連付け（お客様の声・担当スタッフ・監修者）は**対応必須**。ただし**紐付けがない場合は、そのまま下書きを作ってよい**（同日追記）。
- `contracts/case_document.schema.json` の `relations` はオブジェクトとして必須。3つの配列はどれも空でよい（空＝紐付けなし）。
  - `customer_voice_post_ids`、`staff`（`post_id` と `comment`）、`supervisor_post_ids`。
- 空の関連付けは ACF に**書き込まない**（新規なら未設定、既存の下書きなら値を保持）。
  - 担当スタッフは ACF 側で「最低1人」の設定。空のまま作った下書きは、管理画面で保存するときにスタッフの追加を求められる。
- 値は AI が推測しない。利用者・編集者が選んだ投稿IDだけを受け付ける（入力側の `case_input` への反映は C1-C で行う）。
- 紐付けがあるときは、投稿タイプ・公開状態・件数（ACF の min/max）を PHP が現在のACF定義と照合する。

## D-002 共通テンプレートの既知マッピングは「名前」で持つ
- `Mapping/ShipWorksTemplateV11` はフィールド名・レイアウト名だけを使い、field key は保存時に現在の定義から解決する。
- 同じテンプレート名でも構造が違えば `MAPPING_MISMATCH`（AI-010）で止まる。
- フィールド名の一覧は共通テンプレートの知識として公開リポジトリに含まれる。R1（公開）前に、公開してよいか確認する。

## D-003 行・グループは丸ごと置き換え、最上位の未指定フィールドは保持
- 最上位で指定しなかったフィールドは書かない（既存値を保持）。
- 新しく作るリピーター行・フレキシブル行・グループは、指定のない子フィールドを ACF の既定値で埋めてから保存する（古い値が残らないようにする）。

## D-004 テキストのタグ除去
- テーマが一部の text / textarea をエスケープせずに出力しているため、保存時に text は `sanitize_text_field`、textarea は `sanitize_textarea_field`、wysiwyg は `wp_kses_post` を必ず通す。

## D-005 事実は入力された値だけ
- 概要（Outline）には `status=provided` の事実だけを出す。費用・工期は画像からの推測を検証段階で拒否する。

## D-006 対応済みの型（C1-A 時点）
- text, textarea, wysiwyg, url, image, true_false, select, radio, group, repeater, flexible_content, relationship。
- 値を持たない型：tab, message, accordion。
- それ以外（gallery, number, post_object など）は「未対応」として停止する。設計候補にある gallery は未実装。
- 条件分岐の演算子は `==`, `!=`, `==empty`, `!=empty` のみ。他の演算子のフィールドに値を入れようとしたら停止する。

## D-007 スナップショットと復元
- DB トランザクションには頼らず、書き込み前に投稿メタを丸ごと控え、失敗・読み戻し不一致なら戻す。
- 手動復旧用に最新1件を投稿メタへ保存する（C1-D で専用テーブルへ移す予定）。

## D-008 開発専用ツールは `wp-ai-case/dev/` に置き、配布ZIPに含めない
- 合成データの投入・検証・後片付け、自己テスト、表示確認用の期限付きプレビュー。
- プレビューは印の付いた合成データの下書きだけ、トークンのハッシュのみ保存、最長2時間。DB の投稿状態は変更しない。

## D-009 マッピングの持ち方（C1-B）
- 既知マッピング（`ShipWorksTemplateV11`）は「テンプレートの論理名」で値ツリーを作り、`logical_schema()` でその論理構造を宣言する。
- サイトごとの実際の保存先は、版ごとに不変の **bindings**（論理ノード → field key / 名前の経路 / 型 / 変換）として DB（`wpaic_mappings`）に保存する。状態遷移は `wpaic_mapping_events` に記録する（契約 `acf_mapping` / `mapping_transition`）。
- 結び付けは AI を使わないルールだけで行う：前の版と同じキー → 同じ名前 → 見つからなければ「問題」。**別の親への移動は追わない**（未対応として止める）。
- 登録済みの変換：text→textarea、text/textarea→wysiwyg、select↔radio、group→repeater（1行）。これ以外の型変更は未対応。
- 文脈（context_hash）は「投稿タイプ＋実際に適用されるグループ（key と location）」の指紋。タームが違っても適用グループが同じなら同じ文脈。

## D-010 自動で続けてよい変更は「互換」だけ
- マッピングが使うフィールド・レイアウトの定義が1つも変わらず、使っていない部分だけが変わった場合のみ、構造検証を通して自動で新しい版に引き継ぐ（イベント `compatible_update`）。
- それ以外（キーだけの違い・根本変更・未対応・判断できない）は、その文脈の保存を止め、提案 → 構造検証 → ステージング保存・読み戻し → 実表示の確認 → 管理者承認 を経て再開する。
- テーマだけが変わった場合（schema hash は同じ）は保存を止めず、表示の状態を `recheck_required` として区別する。

## D-011 管理者の操作は当面 WP-CLI（GUI は C1-C）
- `wp ai-case mapping status|propose|list|show|history|confirm-display|approve|retire|rollback`。いずれも `manage_options` が必要。
- 管理画面（旧/新の対比・承認ボタン）は C1-C で、顧客向け画面・接続診断と一緒に作る。

## D-012 ステージング検証用の合成下書き作成は、まだ開発ツール（dev/）
- `wp ai-case poc verify-mapping` は合成データと合成画像を使うため dev/ にある。配布版でも管理者がステージングで検証できるよう、C1-C で合成画像を同梱して本体へ移す。

## D-013 契約 v0.6.2（acf_mapping）
- bindings に `layout_key`（レイアウトの結び付け用）、validation に `tested_theme_fingerprint`、未対応時の `problems` を追加。

## D-014 接続診断（C1-C 前半）
- 生成前のローカル確認（`PreflightService`）は外部通信0・ジョブ0・投稿0。順番：権限 → APIキー（AI-001）→ モデル（AI-004）→ 直前の接続テストで分かった認証・権限・モデルの失敗（AI-002/003/004）→ ACFマッピング（AI-010）。
- 管理者のローカル診断（`DiagnosticsService`、契約 `diagnostic_result`）は外部通信をしない。「キー設定済み」を「接続成功」と表示しない。
- 接続テスト（`ProviderProbe`）は管理者の明示操作だけ。費用の可能性への同意、nonce、300秒の間隔、1日10回まで。ユーザーのデータは送らない。結果は分類コードと日時だけを保存し、24時間かモデル変更で「未確認」に戻す。
- エラーは AI-001〜018 の固定文（`ErrorCatalog`）だけで表示し、詳細はサポートID（uuid v4）で管理者だけが参照する。記録する補足情報は許可したキーだけで、秘密・URL・パス・IP・PHP版を消す（`Redactor`）。
- APIキーは `wp-config.php` の定数 `WP_AI_ANTHROPIC_API_KEY` だけから読む。管理画面での入力・保存・表示はしない。

## D-015 顧客向けの通信は REST（サイト側の制限に `wp-ai-case/` の例外を追加）— 2026-11-18 依頼者の決定
- 共通テンプレートのサイトには、管理者以外の REST API を止める Code Snippet「RESTAPIセキュリティ設定」（oEmbed・Contact Form 7 以外は `rest_disabled`）が入っている。
- 依頼者の決定により、この Snippet に `wp-ai-case/` の例外を追加して REST を使う（開発環境のサイトとデモサイトに適用済み。今後デモからコピーするサイトは引き継ぐ）。
- 例外を追加しても、ログイン（Cookie＋`X-WP-Nonce`）と権限の確認はプラグインの `permission_callback` で行う。診断・サポート記録は管理者だけ。`/ping` もログインユーザーだけ。
- ローカル診断で「管理者以外の REST が止められているか」を確認し、止められていれば `rest_transport` を「異常（AI-015）」として、追加する例外のコードを管理者画面に表示する。
- 一時的に検討した admin-ajax 方式は取りやめた。

## D-016 接続テストの送信内容
- 認証とモデルの到達性だけを確かめる最小の呼び出しにする（Models API でモデルを1件取得する想定）。トークンは消費しない見込みだが、レート消費の可能性があるため費用の注意と同意は残す。

## D-017 Claude API は WordPress の HTTP API で直接呼ぶ — 2026-11-18 依頼者の決定
- 公式 PHP SDK（Composer）は同梱しない。多数のサイトへ配る WordPress プラグインで、他プラグインとの依存の衝突（名前空間の付け替えが必要）を避けるため。使う機能も少ない（接続確認・画像つきの生成）。
- `AnthropicClient`：送信先は `https://api.anthropic.com` に固定、`anthropic-version: 2026-10-21`、リダイレクトを追わない、証明書を検証、キーはヘッダーだけ（戻り値・ログに出さない）。
- 接続テストは `GET /v1/models/{model}`。応答は分類コードと表示名だけを使い、生の本文は保存・表示しない。
- その代わり、リクエストの組み立てと API 仕様の変更への追従はこちらで保守する（API バージョンは定数で1か所）。

## D-018 モデルは Claude Haiku 5.5 に固定（2026-11-18 依頼者の決定）
- 画面でのモデル選択はなくした。`Settings::MODEL = 'claude-haiku-5-5'`。
- 接続テストで、モデルが画像入力に対応していないと分かったら AI-004 として止める。
- 生成・修正は構造化出力（`output_config.format` の JSON スキーマ）と `effort: medium`。`temperature` などは送らない。

## D-019 生成ジョブ（C1-C 後半）
- ジョブは DB（`wpaic_jobs`）に保存し、画面からの「進める」（REST `tick`）で1回に外部呼び出し1回だけ進める（WP-Cron に頼らない。Basic認証の環境でも動く）。
- 処理の担当（lease 200秒）を取ってから進め、複数タブでの二重呼び出しを防ぐ。
- 外部へ送る直前に「送信中」を記録。送信中のまま途切れたら結果不明として `needs_recovery`（AI-011）にし、自動では再送しない。再送は利用者の明示操作（料金が再度かかる可能性を表示）。
- 取消し・再試行で世代を上げ、古い呼び出しの結果は捨てる。24時間で期限切れ。
- 同じ `idempotency_key` の再送は同じジョブ。別ユーザーの同じキーは拒否（AI-012）。他人のジョブは見えない（管理者は可）。
- 写真が20枚を超えるときは、20枚ずつ解析してから最後に文章をまとめる（各ステップ＝外部呼び出し1回）。枚数の固定上限は作らない（入力の上限は200枚）。

## D-020 AI の出力の扱い
- AI からは「写真ごとの解析」と「記事の文章（見出し・本文・SEO）」だけを受け取り、事実（facts）は利用者の入力だけから作る（`ResultAssembler`）。
- 写真の集合が依頼と完全に一致しない（不足・重複・架空のID）ときは AI-009 で止める。利用者が指定した工程・キャプションを優先する。
- 外部へ送る写真は、長辺1568pxに縮小し、撮影位置などのメタデータを取り除いたコピー。残っていれば送らない（AI-008）。元の画像は変えない。
- 送るのは一次情報・写真一式の説明・写真の番号/順番/メモ/工程の指定と画像だけ。関連付け・投稿ID・サイトのURLは送らない。

## D-021 修正は型付きの操作だけ
- 画面での修正も AI による修正も、契約 `revision_patch` の操作に限る（`PatchApplier`）。選んだ部分（allowed_sections）以外への変更、未展開の「すべて」、存在しない本文・写真、自由なキーは拒否し、1つでも不正なら何も変えない。
- AI に許す操作は文章・SEO・キャプション・工程・レイアウトだけ。事実の変更・写真の並べ替えや表示の切り替えは画面操作だけ。
- 版の履歴（最大30）を持ち、元に戻す・やり直すができる。画面が見ている版と最新の版が違えば AI-012。

## D-022 開発用の模擬AI（dev/ のみ）
- `wp ai-case poc mock-provider ok` で、外部へ通信しない模擬AIに切り替えられる（結果は【模擬】）。有効な間は「キー設定済み」とみなして画面を試せる（実キーは使わない）。画面に有効であることを表示する。`off` で無効。

## D-023 既存の下書きの修正（mode=revise_draft）
- 対象は、この機能で保存した施工事例の下書きだけ（保存時の文書と各欄の指紋を投稿メタに持つ）。編集画面で作った下書き・公開/予約/非公開の記事は対象外。手作業の記事の内容をACFから読み戻して文書に戻す機能は作らない（任意のレイアウトを正しく戻せないため）。
- 開いた時点の保存済みの文書から始める（外部通信なし）。AIで修正するときだけ、選んだ部分の文章と写真の説明を送る（写真そのものは送らない）。
- 保存では、前回の保存から変わった部分（テンプレートの論理名の単位）だけを書く。書く部分を保存後に人が編集画面で変えていたら、何も書かずに AI-012（部分名を表示）。重ならない部分は保存でき、人の編集は残る。
- 版番号を DB 上で「from のときだけ from+1」に進めてから書く（同じ下書きを2つの画面から保存しても後の方は止まる）。修正中に編集画面で保存された・下書きでなくなった場合も保存しない。
- 入力を消した項目（任意の事実・SEO）は、文字・リピーター・フレキシブルの欄を空にする。条件分岐で隠れるグループ（トップの写真の各型）は触らない。

## D-024 管理画面「マッピング」と、配布版のステージング検証
- WP-CLI と同じライフサイクル（提案 → 構造検証 → ステージング保存・読み戻し → 実表示の確認 → 承認、退役・巻き戻し）を管理画面から行えるようにした（manage_options・nonce）。
- ステージング検証は、検証用の下書き（印 `_wp_ai_case_validation`、【検証用】）をトップの写真3パターン分作り、保存・読み戻しの一致を記録する。画像は GD で作る見本（実在の写真は使わない）。下書きは公開しない。承認時に削除、一括削除もできる。
- 承認済みの版でテーマだけが変わったときは「表示の再確認が必要」と示し、検証用の下書きで確認し直して記録できる（状態は承認済みのまま）。
- 実表示の確認・承認は人（管理者）の判断として記録する。開発作業では、実サイトの承認済みの版の確認・承認は代行しない。

## D-025 新規作成枠（月5件）
- 単位は1サイト・暦月（サイトのタイムゾーン）。生成の開始時に予約し、新しい下書きの保存・読み戻しに成功したら確定、取消し・期限切れで戻す。予約した月に帰属させる。
- 予約は DB の名前付きロック（GET_LOCK、5秒）の中で「確定＋予約 < 上限」を確かめてから入れる。ロックを取れなければ AI-011（超えない側に倒す）。`idempotency_key` は一意。
- 失敗したジョブ（再試行できる状態）の予約は保持する（再試行で二重に数えない）。放置されたジョブは期限切れ（24時間）で戻す。ジョブ作成前の予約は10分の猶予の後に戻す。
- 既存の下書きの修正・AIによる修正・再試行・接続テストは数えない。

## D-026 費用の上限（推定）
- 料金表は版付きで持つ（Claude Haiku 5.5：入力/出力 100万トークンあたり 0.10/0.50 USD〔プロンプト10万トークン以下〕、0.50/2.50 USD〔超える場合〕、キャッシュ読み0.1倍・書き1.25倍。2026-11-18 確認）。フィルターで差し替えられる。
- 外部呼び出しの前に、出力が上限いっぱい（8000）と仮定した推定費用で、月の上限・1回の上限・1日のAI修正の回数を確かめ、超えるなら送らずに AI-014。上限を見直せば同じジョブを再試行できる。
- 呼んだ後は応答の usage から推定費用を記録する（失敗・拒否の応答も）。記録は数値と種類だけ（画像・施主名・ホスト・キー・ヘッダーは書かない）。
- 既定値は月 1.0 USD・1回 0.2 USD・1日 50 回（想定の使用量の数倍で、異常を止めるための値）。`wp-config.php` の定数で変えられる。全体の実額は Anthropic の Workspace／組織の上限で守る。

## D-027 定期の後片付け（Cron の復帰）
- 期限切れのジョブ（世代を上げる）・枠の予約の回収・保存中で止まったジョブの復帰（提案に戻して AI-016。再解析しない）・古い記録の削除（ジョブ30日・使用量400日・サポート記録90日）。
- WP-Cron（毎時）・WP-CLI（`wp ai-case maintenance`。サーバーの cron 用）・管理者の管理画面表示（6時間に1回まで）のどれでも動く。外部通信はしない（ジョブを進めるのは利用者の画面の操作だけ）。
- 診断では、遅れた WP-Cron があるか、後片付けが2日以上動いていなければ AI-011 の警告を出す。

## D-028 配布と更新（R1）
- 配布は GitHub の公開リポジトリのリリースに添付した ZIP（`wp-ai-case-X.Y.Z.zip`、中は `wp-ai-case/` から始まる）。各サイトは同梱の Plugin Update Checker v5.7（MIT、vendor.lock.json で版・コミット・内容の指紋を固定）で12時間ごとに確認し、WordPress の更新画面から更新する。認証トークンは使わない。
- 更新に使うのは「公開済みの最新リリースの添付 ZIP」だけ。PUC の既定の「最新タグ」「ブランチ」への切り替えは止め（タグの push・下書きのリリースでは各サイトに出ない）、GitHub が自動で作るソース一式の ZIP は使わない。`Update URI` ヘッダーで WordPress.org の同名プラグインの更新を受けない。
- 配布 ZIP には dev/（模擬AI・自己テスト・合成データ）と Markdown を入れない。`tools/build_release.py` で再現可能に作り、秘密・版の一致・ヘッダー・ライセンス・同梱物の指紋・PHP構文を検査し、manifest と SHA-256 を出す。秘密の検査は作業ツリーと Git の全履歴。
- CI はタグで **下書き** のリリースを作るだけ。リポジトリの公開・リリースの公開・顧客サイトへの導入は人の事前承認の後（docs/RELEASE.md）。
- 巻き戻しは前の版の ZIP で置き換える（データは残る）。テーブルの変更は列を足すだけにして、前の版でも動くようにする。
- 同梱の readme パーサー（PUC に含まれる）の元のリポジトリにはライセンスの記載がない。公開前のライセンスの確認事項として残す。

## D-029 使う AI の切り替え（Claude／OpenAI。2026-11-18 依頼者の決定）
- Claude API が一時的に使えないため、`wp-config.php` の `WP_AI_CASE_PROVIDER` で Claude（既定）と OpenAI を切り替えられるようにした。モデルはそれぞれ固定（Claude Haiku 5.5／GPT-6 Luna。料金は同じ水準）。画面でモデルを選ぶ機能は作らない。
- キーは選んだ AI の定数だけを読む（`WP_AI_ANTHROPIC_API_KEY`／`WP_AI_OPENAI_API_KEY`）。各プロバイダーは自分の定数しか読まない。値が正しくなければ Claude として扱い、診断で知らせる。
- 依頼の本文・出力の形（JSON Schema）・PHP 側の検証・保存は共通。出力の形は両社の strict モードの共通部分（全項目 required・additionalProperties:false・最上位はオブジェクト）に収める（自己テスト J-29）。
- OpenAI は Responses API（`POST /v1/responses`、`text.format=json_schema`・`strict:true`、`reasoning.effort=medium`、`max_output_tokens=16000`）。**`store=false`** で OpenAI 側に応答を保存させない（既定は保存）。写真は同じ縮小・メタデータ除去済みのコピーを data URL で送る（detail=high）。送信先は `https://api.openai.com` に固定、リダイレクトを追わない。
- エラーは Claude と同じ種別にそろえて分類する。429 のうち残高・支出上限（insufficient_quota・credit_balance_exhausted・spend_limit 系）は請求の問題（AI-003）、それ以外はレート制限（AI-005）。
- 接続テストの前回の結果は、モデルが変われば使わない（切り替え前の AI の結果で止めない）。作成画面の同意文・診断画面・管理者向けの案内は、選んだ AI の名前を表示する。
- 料金表に GPT-6 Luna を追加（0.10/0.50、27.2万トークン超は入力2倍・出力1.5倍）。写真のトークンの係数は公開資料にないため、見積もりは多め（1枚5000）にした。

## D-032 記事の書き方 1.2（2026-11-19 依頼者のフィードバック：手本の事例に合わせる）
- 依頼者が示した手本の事例（人が作った施工事例）に、各フィールドの入れ方をそろえた。テンプレートの版（`TEMPLATE_VERSION`）を 1.2 にした（ACF のグループは同じ「施工事例 ver1.1」）。
- 概要（Outline）：地域 → 建物の種類 → **築年数** → **施工箇所** → 施工内容（**短い一覧**。なければ従来どおり概要の文章）→ 工期 → 費用 → 間取り → 敷地。
- **施主様名**には地域を入れる。**お客様からの声**は入力の文章をそのまま入れる（段落にするだけ）。
- **ご要望・ご提案**は、AI が入力（ご要望・実施した工事・概要）だけからまとめた文章（CaseDocument の節 `request`・`proposal`。種類は custom）。節がなければ入力そのもの（以前の下書きとの互換）。本文（特徴の欄）には出さない。入力の事実は別に残す。
- 施工前：写真（3枚以上は PC 3列、それ以下は 2列）→ 見出し＋文章。施工中：工程ごとに **見出しだけの行 → その工程の写真 → 文章だけの行**（写真は1回だけ使い、どの工程にも入らない写真は最後に見出しなしでまとめる）。施工後：**1枚目を大きく（type-a）**→ 見出し＋文章 → 残りの写真。
- 写真の下の説明文（`_Txt`）は空にし、**短い見出し（`_Title`、AI は20文字程度・最大40文字）**だけを入れる。比較（ビフォーアフター）の文も短い見出しにした。
- AI への指示：タイトルは「【地域】工事の内容｜特徴」、施工中は写真で確かめられる工程ごとに分け、施工中の写真はすべてどれかの工程に入れる（写真のない工程を作らない。見分けられなければ1つにまとめる）。写真から確かめられないことは文章に書かず確認事項に書く（実 API の試験で、合成画像について「画像からは確認できません」と本文に書いたため）。

## D-033 お客様の声・担当スタッフのコメント（2026-11-19）
- お客様の声は **AI に作らせない・書き換えさせない**（入力のまま。AI による修正の操作にも含めない。事実の項目は画像から推測できない項目に入れた）。
- 担当スタッフのコメントは、**入力があればそのまま、空欄なら AI が下書き**する。下書き案の画面と AI による修正（部分「担当スタッフのコメント」・操作 `staff_comment_set`。下書きにある担当者だけ）で直せる。
- AI には担当スタッフの投稿 ID を渡さず、**並び順の番号（1から）**で受け渡す（送信内容に投稿 ID・関連付けを入れない方針を守る）。
- 施工内容の短い一覧は、入力がなければ AI の案を「確認が必要な値」（source `editor_review`）として入れ、画面に「AIの案」と表示する。

## D-036 施工事例カテゴリ・アイキャッチ（2026-11-19）
- カテゴリ（`works_cat`。フィルター `wp_ai_case_category_taxonomy` で変えられる）は、作成画面で選べる。選ばなければ AI が候補（既存のタームだけ。子を持つ分類の見出しは除く）から選ぶ。下書き案の画面で変えられ、保存のときに下書きへ設定する。`works_cat` は ACF の適用条件に使われていないので、マッピングの文脈は変わらない。
- アイキャッチは、施工後の1枚目（なければ最初の写真）を初期値にし、画面で記事に使う写真から選び直せる（「設定しない」も可）。
- これらは版の履歴とは別に持つ（元に戻す・やり直すの対象外）。既存の下書きの修正では、画面で変えたときだけ設定する（開いた後に変えていなければ触らない）。

## D-037 テンプレートの版が上がったときのマッピングの引き継ぎ（2026-11-19）
- 承認済みの版と ACF 定義が同じで、テンプレートの版だけが違うとき、新しい結び付けが**前の版の結び付けをすべてそのまま含み、足しただけ**で構造検証にも合格するなら、承認済みの新しい版を自動で作って引き継ぐ（イベント `template_update`、前の版は退役）。
- 引き継いだ版は**実表示を未確認**にする。マッピング画面に「テンプレートの更新で書き込む項目が増えたため、確認が必要」と出し、表示確認用の下書きで確認・記録できる（保存は続けられる）。
- 引き継げない（既存の結び付けが変わる・見つからない項目がある・増えていない）ときは、構造変更と同じく保存を止め、提案からやり直す。
- 既存の下書きの修正で、保存したときに記録していない項目（テンプレートの更新で増えた項目）は、今も空なら「手で編集した」とみなさない。

## D-038 キャプションに工程の名前を入れない・テーマでの表示のされ方を AI に伝える（2026-11-19 依頼者の指摘）
- テーマ（shipinc）の施工事例詳細は、施工前・施工中・施工後の見出しを自分で出す（`content-works-single.php` の renderSection）。写真の見出し（`_Title`）や節の見出しに工程の名前を入れると重複する。
- AI のキャプションから工程の名前（施工前・施工中・施工後・工事前・完成・ビフォー・アフター など）を除き、残りが「写真」「様子」だけ、または文（〜しました・。で終わる）なら空にする（`ResultAssembler::caption`。AI による修正・取り込みも同じ。利用者が入力したキャプションはそのまま）。
- テーマのテンプレートを読み取り専用で確かめ、表示のされ方を AI への指示に書いた：工程の見出しはテーマが出す／コンセプトの見出しは一覧カードのタイトルにも使う（40文字程度・句点なし）／コンセプトの説明は冒頭に出る（200〜350字）／地域は一覧カードと施主様名で出る。
- 写真の下の説明（`_Txt`）は画像の alt にも使われる。手本の事例に合わせて空にしているので、alt は空になる（手本と同じ）。

## D-039 取り込みで、ページの写真の位置・工程・説明を読み、メディアにない画像も取り込む（2026-11-19）
- 貼り付けた HTML の画像の位置に「[写真n]」の印を入れて AI に送り、写真ごとに「使うか（ロゴ・バナー・スタッフの顔・ほかの事例の画像は使わない）・工程・短い名前」を答えさせる。同じ画像（縮小版・WebP・別ドメインの同じファイル）は同じ番号。写真の一覧は 施工前→施工中→施工後→不明 の順（同じ工程はページの順）に入れ、工程とキャプションは入力欄に入る（利用者が直せる）。
- このサイトのメディアにない画像は、画面から1枚ずつ `POST /import/media` で取り込む（AI は使わない）。公開の http/https だけ（`wp_http_validate_url`・`wp_safe_remote_get`。内部アドレス・file: は拒否）、20MB まで、JPEG/PNG/WebP、200×150 以上。縮小版の URL なら元の大きさを先に試す。画像を包むリンクが画像なら、それを元の大きさとみなす。取り込み元の URL を記録し、同じ URL は再利用する。アップロードの権限（upload_files）が必要。
- 認証のかかったページの画像は取得できない（理由を表示する）。自社のページの写真だけを使うよう画面に書いた。

## D-040 テーマでの表示（表示メモ）（2026-11-19 依頼者と決めた）
- 手で書いた「このテーマではこう表示される」という注意だけでは、テーマの更新や案件ごとの手直しで表示が変わったときに気づけない（例：写真の見出しの「施工前」の重複）。そこで、テーマのテンプレートを読み取り専用で AI に1回送り、欄ごとの表示メモを作る。
- 送るファイル（ThemeReader）：名前に works を含む PHP、そこから get_template_part で呼ばれる部品のうち施工事例の ACF の項目名を使うもの（3段まで）、名前に works を含む SCSS。コンパイル済みの css/・使っていないフレーム（GRA/GRB の別の方）・old_・node_modules・vendor・.history・.git は除く。1ファイル 60KB・合計 240KB まで。送る前に秘密らしい文字列（APIキー・トークン・秘密鍵・パスワードの代入）を調べ、あれば送らない（場所と種類だけ示し、値は出さない）。
- 欄（TARGETS）ごとに「表示されるか・どこに出るか・テーマが自分で出す見出しやラベル（theme_labels）・ほかの使われ方（alt・一覧カードなど）・長さ・書かないこと」と注意をまとめさせる（構造化出力）。知っている欄・短い文字列だけを残す。
- 作ったメモは承認待ち。管理者がマッピング画面（または `wp ai-case display approve`）で確かめて承認したものだけを使う。選んだファイルの内容の指紋が変われば「作り直しが必要」とし、承認済みのメモは使わない。
- 使い方：記事の作成・AI による修正の依頼に入れる（display_notes）。保存前のチェックで、写真の見出し・施工前/中/後の小見出しから theme_labels と同じ言葉を除く（写真の見出しには工程の欄のラベルも使う）。メモがない・使えないときは、標準のメモ（shipinc テーマで確かめた内容）を使う。
- 記事を作るたびにテーマのコードを送ることはしない（毎回の費用がほぼ倍になり、時間も延び、結果もぶれる）。このサイトでの作成は1回 約44秒・$0.008（入力 約5.8万トークン）。
- 保存はオプション（サイトに1つ）。送ったファイルの一覧・指紋・費用・作った人と日時を残し、ファイルの中身は残さない。
- 承認後の本物の試験で、長さの目安（コンセプトの見出し30〜40字・説明200〜350字）が抜けて説明が短くなった（標準のメモに書いていた編集上の目安が、テーマから作ったメモには入らないため）。長さの目安は表示メモではなく記事の書き方のルール（SYSTEM_COMPOSE）に移した。表示メモはテーマから読み取れることだけにする。
- 同じ試験で、本文に「掲載用写真での確認が必要です」という作成上のメモが入った。指示を強め、保存前に写真についての注意・確認のメモの文を除く（`ResultAssembler::prose`。ふつうの文は残す。AI による修正も同じ）。
